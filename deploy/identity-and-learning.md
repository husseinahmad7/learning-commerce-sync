# Identity and the Open edX handoff

**Boundary:** Next.js is the course portal. Open edX is a separate LMS and keeps its own player, authoring UI, API and cookies. The portfolio site is static and never does sign-in. There are no credentials or live services to configure for the portfolio.

## Connect the portal to Keycloak

1. Start a local Keycloak realm or use a development realm you control. Create an OpenID Connect client named `course-portal`, with client authentication and Standard Flow enabled. Disable implicit flow and Direct Access Grants. Require S256 PKCE, and register exactly `http://127.0.0.1:3000/auth/callback` for this local example. For nonlocal origins use HTTPS and exact callbacks.
2. Copy `portal/.env.example` to `portal/.env.local`. Use the realm issuer URL, the portal client identifier and client secret, and a fresh `openssl rand -hex 32` value for `PORTAL_SESSION_SECRET`. Never commit the file. Use the same `PORTAL_ORIGIN` in the browser that you configured in the provider. Portal token endpoint authentication is `client_secret_post`.
3. Start the portal and use **Sign in** with an account in the development realm. In Network you should see redirects and an opaque local session cookie. The portal validates issuer, audience, expiry, nonce and signature via discovery and JWKS, then keeps only encrypted `iss`, `sub`, and display name in that cookie. Access and refresh tokens are neither retained nor sent to the browser. Current session expiry is bounded by the ID-token lifetime and one hour. Sign out clears the portal cookie, not all IdP or LMS sessions.

## Connect Open edX separately

1. Use a separate client (e.g. `openedx-lms`) in the same Keycloak realm. Configure [Open edX third-party authentication](https://docs.openedx.org/en/latest/site_ops/install_configure_run_guide/configuration/tpa/tpa_integrate_open/tpa_oauth.html) for your installed release. For releases that ship [python-social-auth's generic OIDC backend](https://github.com/python-social-auth/social-core/blob/master/social_core/backends/open_id_connect.py), use its issuer/client settings through your release's configuration or Tutor plugin. Confirm the callback path in the LMS configuration and register that exact URI with Keycloak; it is not the portal callback. If your release uses a different backend, follow that release’s guidance and verify its identity validation and account-linking behavior.
2. In `.env.local`, set `LMS_ORIGIN` to the browser-facing origin and `LMS_PY101_PATH` to an existing courseware URL path. The portal only accepts a same-origin LMS path. Give both surfaces the same brand and add an appropriate return-to-portal link in the LMS branding/navigation layer. These LMS changes live in your LMS deployment, not in this repo.
3. Verify in a clean browser: first sign in at the portal, then open the course link and initiate LMS sign-in with the same provider. With a valid provider session and no required consent/account-creation interaction, the browser should return without a second password prompt. Confirm the LMS issues its own cookie, the learner has access, direct deep links work, and an unentitled test account is still denied by the LMS. For existing accounts, verify linkage explicitly; do not match accounts automatically by email alone. A provider can issue pairwise subjects; map identities explicitly when needed.

Prefer separate origins and separate releases. A reverse proxy under a shared prefix is optional, and not enabled here. Before switching, test LMS/MFE base paths, assets, redirects, cookie scope and CORS against the installed release. XBlocks extend course content, not site routing or SSO.
